# `/tdd` as the implementation method; `/feature-dev:feature-dev` deprecated

Implementation work uses `/tdd` — tracer-bullet red-green-refactor against the public surface declared in the agent brief — for every sub-issue, including architectural-shape ones that previously triggered the `/feature-dev:feature-dev` heavyweight gate. The `/feature-dev:feature-dev` orchestration skill (`code-explorer` → 2–3 parallel `code-architect` agents → review pipeline) earned its keep when the right shape was genuinely unclear at implementation time, but PRD-first discipline (ADR 0007) already settles the shape: the PRD picks the architecture, ADRs record the trade-off, and the sub-issue agent brief specifies the public surface. Running architect agents at implementation time mostly re-derives what is already in the PRD. The remaining failure mode — a PRD that did *not* settle the shape — is detected by `/tdd`'s first failing test (you cannot write the test if the contract is ambiguous), which is a cheaper and more honest signal than running three architect agents to discover the same gap; the response is to stop and sharpen the PRD, not to escalate to `/feature-dev`. Cross-module refactors that need shape exploration go through `/request-refactor-plan` per ADR 0007 (refactors are their own PR), not through `/feature-dev`. The `feature-dev:code-reviewer` subagent remains available as one option for cold-read review at PR time alongside `/review`; only the orchestration skill is deprecated. The trade-off is less upfront alternative-generation in exchange for forcing shape decisions into the PRD where they get the durable record they deserve, and for letting implementation be implementation rather than a second design pass.
