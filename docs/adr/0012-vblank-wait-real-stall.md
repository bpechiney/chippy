# vBlank-wait quirk via real `Machine.step` stall, not cycle absorption

`Quirks.vblank_wait_on_draw` (default `true`, vanilla COSMAC VIP) is implemented by having `Machine.step` return the existing-but-previously-unused `StepResult.waiting_for_vblank` variant when the fetched opcode's high nibble is `0xD` (DXYN), the flag is on, and `timing.cycles % (cycles_per_second / 60) != 0` (not on a 60 Hz frame boundary). On stall the function returns early before advancing PC, executing the draw, or emitting any trace / sprite-log line; the same opcode re-fetches on the next `runCycles` iteration and eventually executes when the boundary is reached. `runCycles` requires no special handling: it already increments `timing.cycles` per loop iteration regardless of `StepResult`, which is exactly the "burn the stall cycle" semantics this quirk needs. The contract change this introduces — `cycles ≠ instructions executed` whenever vBlank-wait is active — is documented at the call site (`shouldStallForVblank` carries a brief reference to this ADR) so a future caller writing a tight `step()` loop knows that `.waiting_for_vblank` is a real return code and that its draw will land on the next frame-boundary cycle, not the cycle it was fetched. Two alternatives were rejected: option 2, **cycle absorption** (perform the draw immediately but synthesize "spent" cycles afterward to fake the stall in cycle accounting), would have decoupled PC advancement from cycle counts and broken any Tier-1 trace consumer that relies on `XXXX:OOOO` lines and `cycle=N` sprite-log entries telling a coherent story; option 3, **defer to M5/M6 raylib frame loop** (only honor the quirk when a real wall-clock-driven frame loop drives `step`, leaving `runCycles` quirk-blind), would have made `5-quirks.ch8`'s display-wait test impossible to pass headlessly and contradicted ADR 0003's "no wall-clock in core" invariant by routing correctness through the frontend's timing source. Empirical evidence captured during M3 PRD #67's `/grill-with-docs` pass shows `corax+`'s framebuffer at cycle 1000 is bit-identical (0/2048 pixel diff) under vBlank-wait vs. without — the M2.11 lesson's 3× safety margin absorbed the stall overhead automatically — so M3.3 ships without re-baselining `corax_plus_after_1000_cycles.bin`. The same scratch verification surfaced an unrelated finding: the M2 `ibm_logo_after_30_cycles.bin` golden was captured at a cycle count that *did* fit a vanilla-VIP-incorrect emulator (no stall) but does *not* fit proper VIP semantics — 30 cycles is too tight for the stall path to complete all six letter-draws (132/2048 pixel diff). The empirical stabilization point under stall is N=75; with the M2.11 safety margin the cycle count was bumped to 100 and the golden file renamed accordingly. The captured bytes are byte-identical to the prior N=30 file because the IBM-logo ROM enters a `JP $self` infinite loop after its draws complete and the framebuffer never changes after that — only the cycle count and filename moved, not the visual contract. The trade-off accepted is a contract change to a previously-quiet enum variant in exchange for headless `5-quirks.ch8` correctness and a vanilla-VIP-faithful emulator that ROMs depending on the vBlank stall (e.g. some Octo-built games) will be able to time correctly when M3.4 lands the keystone gate.
