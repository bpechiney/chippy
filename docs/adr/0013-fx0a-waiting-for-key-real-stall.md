# FX0A as `.waiting_for_key` re-fetch with two-phase keypad tracking, symmetric with ADR 0012

`FX0A` (GETKEY) is implemented as a real `Machine.step` stall returning a new `StepResult.waiting_for_key` arm — exactly symmetric in shape with the vBlank-wait stall in ADR 0012 — rather than a pull-from-latch-or-rewind dance. On stall, `step` returns early before advancing PC, executing the side effect, or emitting any trace / sprite-log line; the same opcode re-fetches on the next `runCycles` iteration (which keeps incrementing `timing.cycles` regardless of `StepResult`, so the "cycles ≠ instructions" contract introduced in ADR 0012 generalizes to the second blocking-opcode path) and eventually consumes when its release condition is met. `Machine.runUntil(predicate)` learns to break on `.waiting_for_key` *in addition to* `.halted` (and propagates the variant to its caller), because FX0A — unlike vBlank — has no internal mechanism to advance the stall's release condition without external keypad input, so a tight `runUntil` loop with no other wakeup source must yield to its driver. FX0A's release condition is two-phase, tracked via a `Keypad.awaiting_release: ?u4` claim slot replacing M0's `Keypad.last_released: ?u4` (per CLAUDE.md rule 13 — two overlapping representations of "key release state" violate the rule, so `last_released` is removed, not augmented; semantics shift from "most-recent release ever observed" to "key currently being awaited for release by an active FX0A; null between FX0A invocations"). **Phase 1** (`awaiting_release == null`): if any key in `Keypad.state` is currently down, claim the lowest-indexed held key by setting `awaiting_release = K`. Return `.waiting_for_key` either way. **Phase 2** (`awaiting_release == K`): if `Keypad.state[K]` is still down, return `.waiting_for_key`. Once `Keypad.state[K]` clears, consume the FX0A — write `V[X] = K`, clear `awaiting_release`, advance PC by 2, return `.ran`. Pre-FX0A keypad noise (presses + releases observed before the ROM reaches FX0A) is intentionally discarded — VIP-faithful behavior: only the first key held *after* FX0A is fetched is observed. Two alternatives were rejected: option (a), **consume `last_released` directly inside FX0A** (the M0 shape) — fails on pre-FX0A noise because the latch retains releases that happened seconds before the ROM reached FX0A, so the very first FX0A consumes a key the program never asked the user to press; option (b), **busy-wait inside `step` for an external key event** (loop until `awaiting_release` flips) — violates the cycle-budget contract that `step` returns in O(1) and would deadlock any `runCycles` driver that sources keypad input on the cycle boundary. The save-state byte size of the keypad latch is unchanged: both old (`last_released`) and new (`awaiting_release`) fields encode as a single `u8` with `0xFF` representing `null`, so `Machine.serialize` / `Machine.deserialize` need no version stamping or on-disk migration shim (rule 10) — only the field's *interpretation* changes. The contract change this introduces — `cycles ≠ instructions executed` whenever FX0A is active, and a second non-`.ran`-non-`.halted` arm exiting `runUntil` — is documented at the call site (the FX0A dispatch in `step` and `runUntil`'s switch carry brief references to this ADR) so a future caller knows that `.waiting_for_key` is a real return code, that its consume side effect lands on the cycle the claimed key is observed released (not the cycle FX0A was first fetched), and that `runUntil` callers must be prepared to either re-enter or yield. **Promote at M4 close:** Game Boy's JOYP-poll-into-blocking-IRQ pattern (and Mooneye's wait-for-IRQ test sequences, per the M4.2 retro / handoff) translates directly from this two-phase shape — observe-state-into-claim-slot, wait-for-claim-condition-to-clear, consume — so when M4 closes, lift this cross-reference into `docs/next-target-handoff.md` alongside the existing ADR 0012 vBlank-wait bullet so the Game Boy emulator inherits both halves of "blocking opcode = real `step` stall, not cycle absorption."
