# M3 — Quirks struct + per-opcode behavior gates: retro

Date: 2026-05-03
PRs: [#72](https://github.com/bpechiney/chippy/pull/72) (M3.1), [#73](https://github.com/bpechiney/chippy/pull/73) (M3.2), [#74](https://github.com/bpechiney/chippy/pull/74) (M3.3)
Re-scoped: M3.4 (`5-quirks.ch8` keystone golden) deferred to M4 mid-milestone — see [issue #71](https://github.com/bpechiney/chippy/issues/71).

End state: every flag in the `Quirks` struct (`vf_reset_on_logical`, `shift_in_place`, `jump_uses_vx`, `no_index_increment`, `display_clipping`, `vblank_wait_on_draw`) reads through to a real if-else branch in `Machine.step` or `Framebuffer.xorSprite`, gated paired vanilla / non-vanilla unit tests land beside every gated opcode arm, and the `corax+` golden survives byte-identically under vBlank-wait. ADR 0012 documents the `step()` / `runCycles` contract change (`cycles ≠ instructions executed` whenever a stall fires). The `ibm_logo` golden was re-baselined from cycle 30 → 100 to give the stall path budget — captured bytes unchanged because the IBM logo enters `JP $self` after the draws. `5-quirks.ch8` ROM + `Cosmac-VIP-quirks.png` reference vendored on the preserved `71-quirks-rom-golden` branch (commit `7e0b649`) for M4 to pick up. M3.1–M3.3 ship the *capability*; M4 will provide the *external validation*.

## What worked

- **Per-PR loop scaled to 3 sub-issues with the same green-on-first-CI cadence the M2 retro recorded.** PRD-first → branch → `/tdd` → `/simplify` → `/commit-push-pr` → `/review` → CI matrix → merge, repeated three times. All three PRs landed bit-identical `corax+` and `ibm_logo` regression goldens (the latter at the bumped cycle count).
- **`/grill-with-docs` paid for itself before M3.1 was even branched.** The grilling pass settled the slicing (Y over X, 4 PRs), the vBlank-wait shape (option 1 real-stall over options 2 cycle-absorption / 3 defer-to-M5/M6), the Framebuffer wrap-parameter shape (push down vs gate at call site), and committed the M3.4 acceptance procedure (vendor + pokeRam + reference-screenshot pixel-equality). Zero ADR-grade decisions deferred mid-milestone.
- **Empirical verification before code-write caught two cycle-count surprises ahead of any failing test.** During grilling, a scratch program at `/tmp/verify_vblank/` simulated vBlank-wait against `corax+` in userspace and proved 0/2048 pixel diff at cycle 1000 — locking in the option-1 real-stall choice with measurement, not assumption. Mid-M3.3, the same pattern caught the `ibm_logo` cycle-count-too-tight regression *before* the test went red and surfaced the correct re-baseline target (N=75 stabilization → N=100 with safety margin → bytes byte-identical because the JP-self loop after draws is framebuffer-stable).
- **Cold-read review on PR #74 caught the `cycles_per_second / 60` divide-by-zero edge case** (one-line guard at a real Options-input boundary). Not blocking, deferred as a trivial follow-up — but the mechanism worked exactly as the M0 retro's "include the linked issue body" lesson prescribed.

## What didn't

- **The M3 PRD's M3.4 plan was load-bearing-vibes.** The `pokeRam(0x1FF, 1)` mechanism was settled in grilling as "fully bypasses the only interactive moment this ROM has" — based on the Timendus README's wording about the platform-selection menu, *not* on a trace of what the ROM actually does after the menu. Empirical reality (caught the moment we tried to find the cycle count): the post-menu code path enters a `SKNP V0 / JP self` wait loop at `$204` that requires `EXA1` to fire its skip. `EXA1` is M4 territory. M3.4 was structurally unmeetable as scoped. The fix was to re-scope mid-milestone (re-parent #71 to M4); the lesson is that **PRD validation needs a trace, not a prose reading**, when the acceptance gate is "external test ROM passes."
- **The M3.3 issue body asserted bit-identical `ibm_logo` golden as a regression criterion** — the grilling phase had verified `corax+` survives but never tested `ibm_logo`. The cycle-count-too-tight finding was caught by M3.3-time scratch verification (not a CI red), so the re-baseline landed in the same PR with the correct empirical justification. But the PRD's *prediction* was wrong, and the M3.3 issue body inherited it. Cost: ~10 minutes of confusion + one extra reasoning pass on whether a re-baseline was legitimate. Cheap, but the lesson is that **cite the empirical evidence in the PRD, not just the conclusion** — the PRD said "verified empirically," the issue body should have said "and that verification covered exactly these ROMs at these cycle counts."

## Surprises

- **`runCycles` needed zero changes for the stall semantics.** The vBlank-wait design assumed `runCycles` would need to honor `.waiting_for_vblank` specially. In practice the existing `ran += 1; self.timing.cycles += 1;` per iteration IS the burn-stall-cycle behavior — the `.waiting_for_vblank` return falls through normally, the next iteration re-fetches the same opcode (because `Machine.step` early-returned without advancing PC), and the cycle counter advances to the next frame boundary. Zero diff on `runCycles`. Zero diff on tests of `runCycles` other than the new vBlank-wait integration test.
- **Three of the six quirks were already gated in M2.** `vf_reset_on_logical` had real `if (...) v[0xF] = 0;` lines in the 8XY1/2/3 dispatch arms since M2 — the M3.1 work for those arms was just removing the misleading `// M3:` placeholder comments and adding paired non-vanilla tests. The M3 implementation surface was smaller than the PRD scope suggested. (This validates the M2 PRD's "land vanilla unconditionally with `// M3:` placeholder comments at gated sites" rule from the M2 retro carry-forward — the placeholders correctly named where M3 would land.)
- **No `/diagnose` invocations across the whole milestone, again.** Same observation as M2's retro. Every "test went red" moment was either expected (the tracer-bullet cycles) or the kind of design-time empirical surprise that's better caught by `/grill-with-docs` than by `/diagnose`.

## Carry forward to M4

- **`5-quirks.ch8` ROM + `Cosmac-VIP-quirks.png` reference + the relevant grilling notes are pre-vendored on the `71-quirks-rom-golden` branch** (commit `7e0b649`). M4 can either branch from that head or cherry-pick the M4-prep commit. README entries already document the `RAM[0x1FF]` platform-byte convention and the `EXA1` dependency.
- **The M3.4 sub-issue (#71) is re-parented to M4** — its agent brief still applies post-EXA1 implementation, including the `pokeRam(0x1FF, 1)` mechanism, the empirical-cycle-count procedure, the cross-runner determinism gate, and the `Cosmac-VIP-quirks.png` pixel-equality assertion. Only the "blocked by" list grows: the new M4 keypad sub-issues join #68/#69/#70.
- **`Machine.pokeRam(addr: u12, byte: u8)` test helper still goes with the `5-quirks.ch8` golden PR** — same shape the M3 PRD specified. The bus-private structural refactor stays Game Boy-bound per `docs/next-target-handoff.md`.
- **EXA1 with default keypad state should be enough to pass the wait loop without scripted input.** The trace showed `SKNP V0` with V0=0; default `keypad.state = 0` means key 0 is not pressed, SKNP fires the skip, ROM proceeds. So the M4 implementation of EXA1 — at its simplest — unblocks the `5-quirks.ch8` keystone gate without needing scripted-input infrastructure. (`6-keypad.ch8` will need the scripted-input mechanism; `5-quirks.ch8` likely won't.)

## Carry forward to next emulator (Game Boy)

- **PRD validation needs a trace, not a prose reading, when the acceptance gate is "external test ROM passes."** The M3.4 mis-scope cost a re-shape; the same shape would cost more on Game Boy where mooneye-test-suite ROMs have richer interactive behaviors (waiting on vBlank IRQs, MBC bank-switch handshakes, etc.). For each Game Boy keystone ROM, the PRD's "we've thought about how to drive this" claim must include a trace excerpt + an enumeration of every wait loop / blocking opcode the ROM will hit. `/tmp/verify_*.zig`-style scratch programs are cheap to write and the right disclosing mechanism.
- **Cite the empirical evidence in the PRD, not just the conclusion.** The M3 PRD said "verified empirically during grilling: 0/2048 pixel diff" — but didn't enumerate which ROMs were verified at which cycle counts. The M3.3 issue body inherited the unstated assumption that "verified" meant "all goldens survive," and the `ibm_logo` finding broke that assumption. For Game Boy, every "verified" claim in a PRD should name the ROMs, the cycle counts, and the verification scratch program path — so a future reader can re-run the verification, not just trust the conclusion.
- **Empirical scratch verification (`/tmp/verify_*.zig`) is now a recurring tool.** chippy used it three times during M3 (corax+ vBlank-wait, ibm_logo cycle bump, 5-quirks cycle stabilization). It works because chippy_core's public API is small enough to drive from a standalone Zig file via `zig run --dep chippy_core`. Game Boy will benefit from the same pattern; consider locking in a `verify/` directory inside the Game Boy repo from day one with a `verify/README.md` documenting the build-flag invocation, so the next agent doesn't re-derive the `-Mroot=...` invocation.
