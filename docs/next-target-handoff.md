# Next-target handoff

Forward-looking brief for the next emulator in the chippy → Game Boy → NES → SNES trajectory (see ADR 0010). This file is **living** — bullets get added the moment a chippy lesson crystallizes, not deferred to retro time. At Game Boy kickoff, this is the literal first read; at NES and SNES kickoff, re-read to confirm bullets still apply and promote any rung-specific lessons captured in interim retros.

Each bullet should link back to the chippy retro that motivated it (e.g., "see `docs/retros/M3.md`").

## Do

- **Two-artifact split (core module + thin exe) from day one.** Pays off immediately: CI matrix never resolves a graphics dep, headless determinism is enforceable by construction, the next emulator's test ROMs run on the test runner. (See `docs/retros/M0.md`.)
- **Field-by-field `serialize`/`deserialize` from the first commit, never `std.mem.asBytes` on a struct.** Padding bytes inside structs are ABI- and compiler-version-dependent; raw struct serialization breaks save-state files when fields move. Same shape Game Boy will need across MBC variants and that NES/SNES will need across mapper and expansion-chip variants. (See `docs/retros/M0.md`, reviewer finding on PR #4.)
- **Brief out-of-line comments on "wraps quietly" semantics in core paths that handle ROM-derived addresses.** When chippy's `Bus.read16` masks at 12 bits, the wrap-around on the second byte fetch is non-obvious; Game Boy's 16-bit address space, NES's bank-switched space, and SNES's 24-bit space all have more legitimate boundary conditions, so the same documentation discipline matters more there. (See `docs/retros/M0.md`, reviewer finding on PR #4.)
- **Mechanical `/tdd` gate (ADR 0009) from day one.** A skipped `Skill` invocation on the first chippy M1 attempt cost an entire branch rollback — the agent followed red-green informally but bypassed the Planning phase and left no audit trail. The hook is ~30 lines of bash and zero ongoing cost; ship it before the first Game Boy sub-issue. If a future emulator restores `/feature-dev:feature-dev` per the existing reconsider note, generalize the gate into a configurable mandated-skill framework *before* that milestone starts, not during.
- **Persist the build-artifact cache (`.zig-cache/` or equivalent) between CI runs from the first runnable build.** `magic-nix-cache` preserves `/nix/store` but not the toolchain's own incremental-compile cache, so every PR rebuilds stdlib + dep portions cold. Chippy PR #22 measured a macOS Build step of 81s vs Ubuntu's 27s (3.0× ratio) and Build was the largest controllable line item on both runners. Pattern: `actions/cache@v4` step before Build, key = `${{ matrix.os }}` + hash(`build.zig` + `build.zig.zon` + `flake.lock`) + hash(`src/**/*.zig`), with restore-keys peeling back to OS+build-config, then OS-only, so partial hits still skip stdlib recompilation. Game Boy's surface is larger so the warm-cache savings will be larger too — ship this alongside the GB walking-skeleton CI, not as a follow-up. (See chippy issue #23.)
- **Gitignore Claude Code runtime artifacts (e.g. `.claude/scheduled_tasks.lock`) from the first commit.** The SessionStart cleanup hook (ADR 0011) skips merged-branch auto-cleanup whenever the working tree is dirty, and "dirty" includes untracked per-machine runtime locks written by Claude skills like `/schedule`. The hook logs "skipping" rather than failing, so the cleanup silently stops happening and merged branches accumulate locally. Audit which Claude skills write per-session/per-machine artifacts and ignore them alongside the existing `.claude/worktrees/` entry from the first commit. (See chippy issue #30.)
- **Decide where test fixtures (ROMs, golden snapshots) live BEFORE the first golden test, and pick the embed mechanism to match.** Zig restricts `@embedFile` to paths inside the module's *package directory* (the directory of the module's `root_source_file`). With `chippy_core` rooted at `src/core/root.zig`, the package directory is `src/core/`, so `@embedFile("../../tests/test_roms/...")` is rejected at compile time even though the path resolves. ADR 0004 specified `@embedFile` *and* a `tests/test_roms/` layout — incompatible without action. Three viable shapes: (a) put fixtures inside the module directory (`src/core/test_fixtures/`) and keep `@embedFile`; (b) lift the module's package root to the project root via a top-level wrapper Zig file and keep `@embedFile` with `tests/...` paths; (c) read fixtures at runtime via `std.Io.Dir.cwd()` and accept CWD-coupling + per-test allocation. Chippy chose (c) under time pressure. For Game Boy, pick (a) or (b) up front and write the ADR to match — runtime reads don't compose well as the fixture count grows (mooneye-test-suite etc. is hundreds of ROMs). (See chippy issue #12.)
- **Make the bus's underlying memory array private from the first commit; opcodes touch RAM only through bus methods.** Chippy M2.9 (PR #60) added three new opcodes (FX33/FX55/FX65) that indexed `self.bus.ram[self.cpu.i +% k]` directly. The arithmetic looks fine — `cpu.i` is `u16`, RAM is `[4096]u8` — until you notice `+%` wraps at 16 bits, not 12, so a high-`I` ROM walks past `ram[4095]` and panics the host (rule-12 violation). The neighboring DXYN already routed through `bus.read8` (which masks `& 0x0FFF`), but the pattern wasn't enforced; three independent reviewer agents caught the bug only because they happened to read `bus.zig` for prior art. On Game Boy the bus does *real* work — MBC bank selection, MMIO routing, OAM/VRAM access gating during PPU modes — so direct array indexing is structurally wrong, not just a rule-12 footgun. Either make the memory field unexported (`memory: [N]u8` with no `pub` accessors) so the type system enforces the invariant, or add a CI grep test that flags `bus.ram[` / equivalent outside the `Bus` module from the first commit. (See chippy PR #60, issue #61.)
- **Verify test-ROM goldens against published reference screenshots, not just locally-captured snapshots.** chippy M2.11 (PR #64) compared the corax+ packed framebuffer pixel-by-pixel against `Timendus/chip8-test-suite/pictures/corax+.png` (sample each cell, decode to packed bits, `expectEqualSlices` against the captured golden). The local snapshot proves *determinism*; the reference comparison proves *correctness against an external authority*. Mooneye, blargg, and dmg-acid2 all ship reference outputs and screenshots — bake the comparison into the golden test from day one. Same code shape works (PNG → packed bits → equality assertion). (See `docs/retros/M2.md`.)
- **Pick test-ROM cycle counts from empirical measurement, not PRD estimates.** chippy M2.11's PRD estimated corax+ stabilizes at 10k–50k cycles; reality was ~350. Game Boy frame counts are roughly four orders of magnitude over chippy's so the temptation to anchor on a "round number" estimate will be stronger; resist it. Procedure: run the ROM with `--print --cycles N` at increasing N (binary-search if needed), hash the rendered framebuffer at each N, take the smallest N where the hash stabilizes across consecutive samples, then add a generous safety margin (chippy used ~3×). (See `docs/retros/M2.md`.)
- **Tier 1 trace writer's line format is per-emulator, not shared across the trajectory.** chippy froze `XXXX:OOOO MNEMONIC <state-delta>` at M2.10 (PR #63). Game Boy's per-cycle state is much richer (16-bit registers, MBC bank, PPU mode, IF/IE flags); decide GB's trace format up front during the M0/M1-equivalent and resist trying to share chippy's exact bytes. A forced-shared format would be a leaky abstraction at the trace boundary, not a clean reuse — different emulators have different state shapes. The `TraceSink` *seam* (sink-shaped opt-in interface, no allocation, no work when null) carries forward; the *format* does not. (See `docs/retros/M2.md`.)
- **PRD validation needs a trace, not a prose reading, when the acceptance gate is "external test ROM passes."** chippy M3.4 was scoped on the Timendus README's prose claim that `pokeRam(0x1FF, 1)` "fully bypasses the only interactive moment." The grilling pass settled the design on that claim. Empirical reality (caught the moment we tried to find the cycle count): the ROM enters a `SKNP V0 / JP self` wait loop at `$204` immediately after the platform-byte read — which requires `EXA1` to fire its skip. `EXA1` is a future-milestone feature (chippy M4); M3.4's acceptance gate was structurally unmeetable as scoped, and got re-parented mid-milestone. Game Boy mooneye-test-suite ROMs have richer interactive behaviors (waiting on vBlank IRQs, MBC bank-switch handshakes, JOYP polling), so the same scoping mistake will be more expensive there. **Procedure: for each test-ROM keystone gate the PRD names, the grilling phase must produce a trace excerpt (e.g. via `/tmp/verify_*.zig`) that walks past every wait loop and blocking opcode the ROM hits, and the PRD must enumerate every such opcode the implementation needs to pass before the gate fires.** Same `/tmp/verify_*.zig`-style scratch programs that worked for chippy work the same way for GB. (See `docs/retros/M3.md`.)
- **Cite the empirical evidence in the PRD with explicit ROM names + cycle counts, not just a conclusion.** chippy's M3 PRD said "verified empirically during grilling: 0/2048 pixel diff" without naming WHICH ROMs were verified at WHICH cycle counts. The M3.3 issue body inherited the unstated assumption that all goldens survive vBlank-wait — but the verification covered `corax+` only, not `ibm_logo`. The `ibm_logo` cycle-count-too-tight regression got caught by mid-PR scratch verification, but the PRD's prediction was wrong, and the issue body inherited the wrong claim as a "regression gate." For Game Boy, every "verified" claim in a PRD must name the ROMs, the cycle counts, and the verification scratch program path — so a future reader can re-run the verification, not just trust the conclusion. (See `docs/retros/M3.md`.)
- **Empirical scratch verification (`/tmp/verify_*.zig`) is now a recurring tool — codify the build-flag invocation.** chippy used it three times during M3 (corax+ vBlank-wait survival, ibm_logo cycle bump, 5-quirks cycle stabilization) plus mid-grilling. It works because chippy_core's public API is small enough to drive from a standalone Zig file via `zig run --dep chippy_core -Mroot=verify.zig -Mchippy_core=path/to/root.zig`. Game Boy will benefit from the same pattern — and ideally from the same invocation locked into a `verify/` directory inside the GB repo from day one with a `verify/README.md` documenting the build-flag invocation, so the next agent doesn't re-derive `-Mroot=...` or copy fixture files into `/tmp` to satisfy `@embedFile`'s package-path constraint. (See `docs/retros/M3.md`.)
- **Review findings flagging test-case gaps or convention drift cannot be deferred on speculation.** chippy PR #81 (M4.1) deferred two reviewer findings as "non-blocking follow-up" — one test-case gap (the `V[X] & 0xF` masking contract was implemented via `@truncate` but untested) and one convention drift (every shipped opcode has a `disasm` entry; EX9E/EXA1 were shipped without one). Both rationalizations were prose-grounded, not evidence-grounded — same anti-pattern as the M3.4 PRD scoping on the Timendus README's prose claim that `pokeRam(0x1FF, 1)` "fully bypasses the only interactive moment" (see the PRD-validation-needs-a-trace bullet above). The norm is now CLAUDE.md rule 13. For Game Boy, ship the rule from day one. If a *second* deferral-mode review failure occurs (chippy or GB), build a chippy-local `/review-strict` wrapper skill before the next milestone — phrase-blacklist hooks are too brittle (false positives erode trust per ADR 0011's flake-tolerance budget) and the `feature-dev:code-reviewer` plugin prompt isn't chippy-controlled. (See chippy PR #81.)
- **Test-ROM golden runner choice (cycles vs frames) is a load-bearing setup decision; encode the rationale in the test docstring.** chippy's three goldens split: corax+ and ibm_logo use `runCycles`; 5-quirks uses `runFrame`. The deciding question is whether the ROM uses the delay timer for animation pacing or wait-for-key behavior — if yes, `runFrame` is mandatory because `runCycles` advances the CPU but does not call `timing.tick()`. chippy M4.2 originally used `runCycles(15000)` by copy-paste from corax+, captured the splash screen indefinitely, and required a mid-PR pivot once a render of the captured `.bin` revealed it was the splash, not the post-test results. **Procedure for Game Boy: every test-ROM golden's setup must justify the cycle/frame loop choice in its docstring (which timer/IRQ-driven behaviors the ROM relies on); reviewer agents should flag missing justifications.** Game Boy's PPU mode timing, vBlank/STAT IRQ handling, and APU sample generation amplify the same trap — pick the loop primitive based on what the ROM actually does, not by copy-pasting the previous golden. (See chippy PR #82.)
- **Vendored reference images must be raw rasters at integer multiples of native resolution, not marketing screenshots.** chippy M4-prep vendored `Cosmac-VIP-quirks.png` (848×661, **not** an integer multiple of 64×32) from upstream's `pictures/` dir as the eyeball-gate anchor. Mid-PR reality: it's a screenshot of the Emma 02 emulator window inside macOS desktop, with multiple visible windows and OS chrome — useless as a pixel reference. The neighboring `pictures/quirks.png` (768×384, clean 12× upscale, no chrome) is the actual reference. The `848 / 64 = 13.25` non-integer ratio was the immediate tell; we missed it because the vendoring step didn't open the file. **Procedure: before committing any reference image, (a) verify dimensions are an integer multiple of the emulator's native framebuffer, and (b) open the file and confirm it's a raw rasterization — no OS chrome, no emulator UI, no window decorations.** Game Boy's mooneye-test-suite, dmg-acid2, and blargg references are well-defined raw rasters but always visually inspect first. (See chippy PR #82.)
- **Pre-flight ROM trace must sample multiple cycle windows — boot, mid-test, post-test, idle — not just the boot phase.** Refines the existing PRD-validation-needs-a-trace bullet above. chippy M4.2's pre-flight trace at cycle 50 000 (still in the splash phase) confirmed only EXA1 was hit as a blocking opcode and concluded "FX0A is not exercised post-patch." Empirical reality (caught only after the captured `.bin` was rendered and shown to be wrong): the ROM hits FX0A 2 874 times in 9.8M cycles, mostly in the post-test wait-for-key-to-restart loop — a phase the pre-flight trace never reached. The PRD's "FX0A out of scope" claim was wrong, costing a mid-PR FX0A implementation pivot. **Procedure for Game Boy: the pre-flight trace must enumerate every distinct opcode hit across at least three sample windows (boot/post-boot, mid-test, post-test), and the PRD must list every blocking-opcode dependency the ROM expresses across the full execution.** The existing `verify/`-style scratch pattern handles this — just budget for multiple sample windows instead of one. Mooneye's wait-for-IRQ and JOYP-poll sequences make this even higher-stakes for GB. (See chippy PR #82.)
- **Pre-build the golden-test harness on the *second* test, not the third.** chippy waited for the rule of three (ibm_logo, corax+, 5-quirks all carrying byte-identical load-rom → run → pack → compare-or-rebaseline copies) before extracting `src/core/golden_harness.zig` (PR #86 closing #83). The deep-module shape that landed — `runAndCompare(opts: RunOptions)` where `opts.run` is a `RunMode = union { cycles, frames }` and `opts.pre_run` is an optional `*Machine`-mutating hook — naturally absorbs the cycles-vs-frames decision from the bullet above *and* per-ROM setup variation (chippy's 5-quirks needed `pokeRam(0x1FF, 1)`; GB's mooneye/blargg ROMs will need MBC bank-select bytes, IF/IE flags, JOYP state, etc.). Game Boy will have hundreds of test-ROM goldens (mooneye-test-suite alone), not three — pre-extract the harness alongside the second golden so the third through Nth land as one-line `runAndCompare` invocations from the start. Plan for additional `RunOptions` fields the GB harness will need from day one: `init_opts: Machine.Options`, custom assertion callbacks (some mooneye ROMs signal pass/fail via register state, not framebuffer), and frame-window snapshot sequences (animations). (See chippy PR #86.)
- **Eyeball-gate path should render the captured `.bin` standalone, not depend on the frontend's input plumbing.** chippy M4.2's original acceptance criterion said "render in TUI and visually compare against the reference PNG." But chippy's TUI has no keyboard input wired (issue #84), so interactive ROMs like 5-quirks can't dismiss their platform-select menu — `just run tests/test_roms/quirks.ch8` sits on the menu screen forever. Workaround that worked: a tiny standalone render utility (`/tmp/bin2ppm.zig`, ~30 LOC) that takes a `.bin` path and emits a PPM file (macOS Preview opens PPM natively, no host deps via `nix develop -c zig run`). **For Game Boy: ship a `verify/render_bin.zig`-style utility in the GB walking skeleton from day one, so the eyeball-gate is decoupled from the frontend's input plumbing and works for every test-ROM golden, regardless of whether the GB frontend has joypad input wired yet.** (See chippy PR #82, issue #84.)
- **The M2.11 "smallest stable N" cycle-count procedure breaks down on framebuffers that are deterministic but oscillate** (cursor blinks, palette flips, sprite-flicker animations, scrolling marquees). chippy M4.4's `keypad-menu.png` reference shows the menu cursor visible; the menu's blink loop alternates the framebuffer hash every ~5 frames at 700 Hz CPU / 60 Hz tick, so there is no permanently-stable N — only ~150-cycle-wide plateaus. Fine-grained sweep at 50-cycle resolution found the first "cursor-visible" plateau (1900–2000 cycles) that pixel-matches the reference. Procedure for Game Boy: when the M2.11 sweep doesn't show a permanent plateau, switch to fine-resolution probing of the cycle space, identify the plateau bounds for each oscillation phase, and pin the checkpoint cycle to the plateau matching the reference image. Pinning to the *centre* of a plateau is more robust than the edge. The "round to nearest 1000" guideline is overridden by plateau width — pick the cycle that lands cleanly inside the plateau, not the round number that may straddle a phase transition. Mooneye's PPU mode-driven blink tests, dmg-acid2's sprite-flicker frames, and any blargg ROM with on-screen "OK"/"FAIL" cursors will hit the same trap. (See chippy PR #92.)
- **Test-only drivers that step a `Machine` cycle-by-cycle should route through `Machine.runCycles(1)` rather than parallel the cycle-counting + halt-detection logic.** chippy M4.4's `scripted_input.zig` initially mutated `m.timing.cycles += 1` directly inside its per-cycle loop, paralleling the same lines that already live inside `Machine.runCycles`. Cold-read review flagged this as a leaky abstraction: any future contract change to `runCycles` (e.g. a new `StepResult` arm that *doesn't* count as a cycle, or a real-time-clock interaction in the GB rung) would silently diverge in the helper. The fixed shape — `if (m.runCycles(1) == 0) return error.UnexpectedHalt` — inherits the contract. Game Boy's mooneye-test-suite drivers (waiting on STAT-mode IRQs, JOYP transitions, MBC handshakes) will need the same per-cycle granularity for sub-frame event timing; ship the equivalent helper from day one with `runCycles(1)` routing baked in, never `step()` + manual `timing.cycles` bookkeeping. (See chippy PR #92.)
- **Blocking opcodes are real `step` stalls, not cycle absorption — and the claim-slot pattern generalizes to multi-phase release conditions.** chippy ships two living examples: ADR 0012 (DXYN's `vblank_wait_on_draw` quirk → `StepResult.waiting_for_vblank`, single-phase) and ADR 0013 (FX0A GETKEY → `StepResult.waiting_for_key`, two-phase via `Keypad.awaiting_release: ?u4` claim slot). The shared shape: on stall, `step` returns early before advancing PC, executing the side effect, or emitting any trace / sprite-log line; the same opcode re-fetches on the next `runCycles` iteration; `runCycles` keeps incrementing `timing.cycles` regardless of `StepResult` so the "cycles ≠ instructions executed during a stall" contract holds; `runUntil(predicate)` learns each stall arm and propagates it to its caller (no internal mechanism advances FX0A's release condition without external input, so a tight `runUntil` loop must yield to its driver). Two-phase generalization for FX0A: phase 1 (`awaiting_release == null`) claims the lowest-indexed held key, returns `.waiting_for_key`; phase 2 (`awaiting_release == K`) waits for `Keypad.state[K]` to clear, then consumes (writes `V[X] = K`, clears the slot, advances PC, returns `.ran`). Pre-claim noise is intentionally discarded — only state observed *after* the opcode is fetched counts. Game Boy's JOYP-poll-into-blocking-IRQ pattern, Mooneye's wait-for-STAT-mode and wait-for-IRQ sequences, and `HALT` / `STOP` opcodes all map directly onto this shape — observe-state-into-claim-slot, wait-for-claim-condition-to-clear, consume. Ship a `StepResult` union with a `BlockingReason` axis (or N parallel arms — chippy used parallel) from the GB walking skeleton so the third blocking-opcode shape doesn't trigger a third union-arm migration. (See chippy ADR 0012, ADR 0013, PR #74, PR #89.)
- **CI: path-filtered with always-running gate from day one.** Heavy build/test should not run on docs-only / hooks-only / ADR-only diffs. Pattern: a `changes` job (native `git diff` against `pull_request.base.sha` / `push.before` + `grep -qvP` against a deny-list regex) sets `code=true` for any file outside docs/hooks; a matrix `test` job gates on `code=true`; a tiny always-running `required` job (`needs: [changes, test]`, `if: always()`) is the **sole** branch-protected check — passes vacuously when `test` was skipped, fails iff `changes` errored or `test` failed/cancelled. Deny-list (fail-open: forgetting an entry wastes runner time, allow-list would silently skip an untested merge). Single workflow (no two-file inverse-mirror drift). Native shell instead of `dorny/paths-filter` because the trigger surface is tiny (no force-push to a protected branch, no fork PRs, no schedule/workflow_dispatch); revisit only if multi-group filters appear. **Two-pass `.github/` split:** the deny-list excludes `^\.github/(?!workflows/)` (PCRE negative lookahead, requires `grep -P` → ubuntu-only `changes` job) so dependabot configs / issue templates / labelers skip heavy CI while workflow file changes still trigger the integration test against the real `nix develop -c zig build` invocation. The `^[^/]+\.md$` clause is anchored to single-segment paths so a hypothetical `src/INTERNALS.md` is not silently misclassified as docs. (See chippy issue #20.)

## Avoid

- **`cachix/install-nix-action` on macOS runners.** Pre-provisioned `_nixbld1` collides with `eDSRecordAlreadyExists`. Use `DeterminateSystems/nix-installer-action@v17` instead. **Don't pair it with `magic-nix-cache-action@v9`:** officially deprecated 2025-02-01, currently no-ops on save/restore (`Cache service responded with 400`), and added 9–13s of pure overhead per chippy job. For chippy-scale Nix closures (handful of stock nixpkgs + one pinned toolchain) `cache.nixos.org` covers cold runs adequately. Larger Nix closures may justify `DeterminateSystems/flakehub-cache-action@v9` — but that needs a `permissions:` block (`id-token: write`, `contents: read`) plus a FlakeHub.com signup, so weigh the auth-surface and signup cost against measured savings before adding it. (See `docs/retros/M0.md`, chippy issue #25.)
- **Cold-read reviewer agents without the linked issue body.** The `feature-dev:code-reviewer` agent run on PR #4 read `CLAUDE.md`, `CONTEXT.md`, the ADRs, and the diff — but did **not** fetch the GitHub issue listing the acceptance criteria, and so flagged in-spec methods (`runUntil`, `deinit`) for removal. **For the next emulator, every reviewer-agent prompt must include either the issue body inline or an explicit `gh issue view` instruction.** (See `docs/retros/M0.md`.)
- **GitHub task-list checkboxes with descriptive prefixes.** `- [ ] **M0 — ...** → #1` does not auto-tick when #1 closes; only the bare `- [ ] #1` form does. Future roadmaps should use the bare form, or accept manual ticks. (See `docs/retros/M0.md`.)

## Reconsider

- **Tier 2 CLI debug REPL was deferred to "on demand" for chippy.** Game Boy per-frame instruction count is roughly four orders of magnitude over chippy's (~70k cycles/frame at 4 MHz vs ~12 cycles/frame at 700 Hz), and full state no longer fits in a `std.debug.print`; revisit at Game Boy kickoff whether the REPL should land in the GB walking skeleton rather than waiting for a forcing function. NES and SNES amplify the same argument.
- **The `serialize` save-state format is currently field-by-field with no version header.** Fine for chippy (one schema version, lifetime measured in months). For Game Boy onward — multiple MBC variants, eventual save-state forwards-compat across the trajectory — add a 4-byte magic + 2-byte version at the front from the first GB commit.
- **CI runs `nix develop -c zig fmt --check`. The `fmt` step is currently after build and tests** — fast-failing is generally better. Reorder for the next emulator so a formatting violation is the first red.
- **Cross-model adversarial review (e.g., Codex reviewing Claude PRs).** Considered for chippy 2026-05-02 and deferred. The evidence base is thin — self-consistency, multi-agent-debate, and LLM-as-judge literature exists, but nothing rigorous specifically on cross-model adversarial code review reducing shipped bugs. For chippy the single Claude reviewer + CI matrix has been sufficient. For Game Boy and beyond the shared-blind-spot risk grows with codebase size, so revisit at Game Boy kickoff. **Hard enforcement is the bar** — if it can't ship as a CI job + branch-protection check (server-side, not Claude self-policing), skip it. If pursued: run as a non-blocking GitHub Actions job for ~10 PRs first, track findings vs false positives, flip to blocking only if Codex catches ≥1 real issue the Claude reviewer missed across that trial. Otherwise delete the workflow and record the negative result here.
- **`/feature-dev:feature-dev` was deprecated for chippy in favour of `/tdd` as the universal implementation method (ADR 0008).** It worked because PRD-first discipline (ADR 0007) settles shape before implementation, and chippy's surface is small enough that one architect's read of the PRD is enough. Game Boy has more legitimate shape ambiguity (MBC variants, sub-instruction M-cycle/T-cycle accuracy, GBC variant decision, save-state forwards-compat). Decide at Game Boy kickoff whether to keep `/tdd`-only or restore `/feature-dev:feature-dev` for genuinely ambiguous milestones — driven by whether the PRD process is producing settled-enough public surfaces, not by milestone size alone.
